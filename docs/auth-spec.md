# BookNest — Технічне завдання: форми автентифікації

**Модуль:** Реєстрація · Вхід · Відновлення паролю
**Версія:** 1.0 · **Дата:** 2026-06-06 · **Статус:** до реалізації
**Кодова база:** `src/v1/register.html`, `src/v1/login.html`, нова сторінка `src/v1/reset.html`
**Стек:** статичний HTML + CSS + TypeScript/vanilla JS, без фреймворку.
**Дизайн-система:** `src/tokens.css`, `src/typography.css`, іконки `src/icons.svg`.

## 1. Загальні положення

### 1.1. Мета
Реалізувати клієнтську валідацію та поведінку трьох форм автентифікації з єдиним підходом
до перевірок, повідомлень про помилки, доступності й адаптивності. Документ описує **клієнтську**
частину. Усі правила, позначені 🔒, мають **обов'язково дублюватися на сервері** — клієнтська
валідація лише для UX, вона не є захистом.

### 1.2. Спільні принципи
- **Мова інтерфейсу:** українська. Тон повідомлень — дружній, як у наявних формах
  («Введіть ваше ім'я», «Рада знову тебе бачити»).
- **Теми:** світла / темна — уже реалізовано (`data-theme`, `theme-fab`). Нові елементи
  використовують лише змінні з `tokens.css`, без хардкоду кольорів.
- **Адаптивність:** брейкпоінти `900px` і `560px` (як у наявному CSS). На мобільному
  hero-колонка ховається.
- **Без сторонніх бібліотек** для валідації — лише нативний JS + регулярні вирази нижче.
- **Форми мають `novalidate`** (вимикаємо браузерні бабли) — усі перевірки робить наш код.

### 1.3. Повторне використання наявних класів
Розробник **не вигадує нову розмітку станів**, а використовує те, що вже є:

| Призначення | Клас / прийом |
|---|---|
| Контейнер поля | `.field` (+ `id` для доступу з JS, напр. `fEmail`) |
| Стан помилки поля | додати `.invalid` на `.field` |
| Текст помилки | `.err` всередині `.field` (показується через `.field.invalid .err`) |
| Підказка під полем | `.hint` |
| Індикатор надійності паролю | `.strength` + `.bar.on` + `.strength.full` |
| Обов'язкове поле (зірочка) | `.label--required` |
| Необов'язкове поле | `<span class="opt">(необов'язково)</span>` |
| Банер успіху | `.alert.show` |
| Показ/приховування паролю | `.pwtoggle` + іконки `#i-eye` / `#i-eye-off` |

## 2. Загальні вимоги до валідації (для всіх форм)

### 2.1. Коли запускати перевірку (стратегія тригерів)
Гібридна модель — найкращий UX:

1. **При сабміті** — повна перевірка всіх полів. Якщо є помилки: не відправляти,
   підсвітити всі невалідні поля, **фокус на перше невалідне поле**, проскролити до нього.
2. **При втраті фокусу (`blur`)** — перевіряти конкретне поле, якщо користувач уже щось у нього вводив.
3. **При введенні (`input`)** — поле перевіряється на льоту **тільки після того, як воно вже
   позначалося невалідним** (тобто помилку прибираємо одразу, щойно її виправили; нову помилку
   на першому символі не показуємо, щоб не дратувати).

> Правило «не лай, поки не помилився, але хвали одразу після виправлення».

### 2.2. Нормалізація вводу (перед перевіркою)
- Усі текстові значення — `trim()` по краях.
- E-mail — додатково `toLowerCase()`.
- Ім'я / нікнейм — згортати повторні внутрішні пробіли (`«Анна   Марія»` → `«Анна Марія»`).
- Перевіряти **нормалізоване** значення; у поле повертати нормалізоване при `blur`.

### 2.3. Доступність (a11y) — обов'язково
- Невалідний `input` отримує `aria-invalid="true"` (валідний — `false` або атрибут знімається).
- Повідомлення `.err` має `id`; на `input` ставиться `aria-describedby="<id помилки>"`.
- Блок помилки — `role="alert"` (зчитувачі озвучують появу).
- Усі поля мають `<label for>` (уже є). Іконки-кнопки (показ паролю, тема) мають `aria-label`.
- Керування з клавіатури: усі інтерактивні елементи (жанри-чипи, соц-кнопки) досяжні Tab,
  активуються Enter/Space, мають видимий `:focus-visible`.

### 2.4. Стани поля (візуальні)
| Стан | Опис |
|---|---|
| `default` | стандартна рамка `var(--border)` |
| `focus` | рамка `var(--primary)` + кільце `var(--focus-ring)` (вже в CSS) |
| `invalid` | рамка `var(--danger)`, видимий `.err` |
| `valid` *(нове, опційно)* | за бажанням — лаконічна позначка ✓ праворуч для критичних полів (e-mail, нікнейм). Не обов'язково. |

### 2.5. Поведінка кнопки сабміту
- Захист від подвійного натискання: на час «відправки» кнопка `disabled` + текст/спінер «Зачекайте…».
- Після відповіді сервера — повернути активний стан.
- На формі реєстрації кнопка **заблокована, доки не поставлено згоду** (уже реалізовано через `terms`).

### 2.6. Класифікація повідомлень
- **Польові** — під конкретним полем (`.err`): формат, довжина, обов'язковість.
- **Загальні (form-level)** — окремий банер угорі форми: «Невірний e-mail або пароль»,
  «Забагато спроб, спробуйте за 5 хв», «Сервіс недоступний». Для цього додати банер помилки
  за аналогією з `.alert`, але у стилі `--danger` (напр. `.alert.alert--error`).

## 3. Сторінка «Реєстрація» (`register.html`)

### 3.1. Функціонал
Поля та елементи (зліва направо, зверху вниз):

1. **Ім'я** — обов'язкове.
2. **E-mail** — обов'язкове.
3. **Пароль** — обов'язкове, з індикатором надійності та показом/приховуванням.
4. **Підтвердження паролю** — обов'язкове, з показом/приховуванням.
5. **Нікнейм** — необов'язкове.
6. **Дата народження** — необов'язкове.
7. **Згода з Умовами та Політикою** — обов'язковий чекбокс (розблоковує кнопку).
8. **Кнопка «Зареєструватися»**, далі соц-логін (Google / Apple), банер успіху.

### 3.2. Валідація полів

#### 3.2.1. Ім'я (`#name`) — обов'язкове 🔒
| Правило | Значення |
|---|---|
| Не порожнє після `trim` | так |
| Мін. довжина | 2 символи |
| Макс. довжина | 50 символів |
| Дозволені символи | літери (укр + лат), пробіл, апостроф `'` / `’`, дефіс `-` |
| Має містити | щонайменше одну літеру (не лише дефіси/пробіли) |
| Заборонено | цифри, спецсимволи, емодзі, подвійні пробіли (нормалізувати) |

Regex: `^[A-Za-zА-Яа-яЁёІіЇїЄєҐґ' ’\-]{2,50}$` (плюс окрема перевірка «є хоча б одна літера»).

Повідомлення:
- порожнє → «Введіть ваше ім'я»
- < 2 → «Ім'я має містити щонайменше 2 символи»
- > 50 → «Ім'я задовге (максимум 50 символів)»
- недозволені символи → «Ім'я може містити лише літери, апостроф та дефіс»

#### 3.2.2. E-mail (`#email`) — обов'язкове 🔒
Поточний regex у коді надто слабкий (`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`). Замінити на строгіший.

| Правило | Значення |
|---|---|
| Не порожнє | так |
| Нормалізація | `trim` + `toLowerCase` |
| Макс. довжина | 254 символи (RFC 5321) |
| Локальна частина | 1–64 символи, без крапки на початку/кінці, без подвійних крапок `..` |
| Домен | хоча б одна крапка, TLD ≥ 2 літери, без пробілів |
| Заборонено | пробіли, кирилиця в адресі (для MVP), два `@` |

Regex (практичний): `^[A-Za-z0-9._%+\-]+@[A-Za-z0-9.\-]+\.[A-Za-z]{2,}$`
Додаткові перевірки кодом: немає `..`, локальна частина не починається/закінчується крапкою, довжина ≤ 254.

Повідомлення:
- порожнє → «Введіть ваш e-mail»
- невірний формат → «Невірний формат e-mail»
- задовгий → «E-mail задовгий»

*(Опційно, приємний бонус): підказка при типовій помилці домену — `gmial.com` → «Можливо, ви мали на увазі gmail.com?»*

#### 3.2.3. Пароль (`#pw`) — обов'язкове 🔒
Політика (рекомендована, узгодити із замовником):

| Правило | Значення |
|---|---|
| Мін. довжина | 8 символів |
| Макс. довжина | 64 символи |
| Великі літери | ≥ 1 |
| Малі літери | ≥ 1 |
| Цифри | ≥ 1 |
| Спецсимволи | ≥ 1 (рекомендовано; як мінімум — 3 з 4 класів) |
| Без пробілів по краях | так |
| Не дорівнює e-mail / імені / нікнейму | так (порівняння без регістру) |
| Не зі списку поширених | `123456`, `password`, `qwerty`, `11111111`, `12345678` тощо (короткий блок-лист) |

**Чек-лист вимог замість одного повідомлення.** Під полем показувати динамічний список умов,
кожна підсвічується ✓/✗ у реальному часі (UX набагато кращий, ніж одне «Мінімум 8 символів»):
- ✓/✗ Щонайменше 8 символів
- ✓/✗ Велика і мала літери
- ✓/✗ Хоча б одна цифра
- ✓/✗ Хоча б один спецсимвол

**Індикатор надійності** (`.strength`, 4 бари) — уже частково є в `register.js`. Логіка балів:
```
score = 0
+1 якщо довжина ≥ 8
+1 якщо є велика І мала літери
+1 якщо є цифра
+1 якщо є спецсимвол
бонус: довжина ≥ 12 підвищує рівень
```
Відображення: 0–1 бар — «Слабкий», 2–3 — «Середній», 4 — «Надійний» (`.strength.full`, колір `--success`).

Повідомлення при сабміті (якщо політика не виконана) → «Пароль не відповідає вимогам безпеки»
(а конкретику показує чек-лист).

#### 3.2.4. Підтвердження паролю (`#pw2`) — обов'язкове
| Правило | Значення |
|---|---|
| Не порожнє | так |
| Точний збіг із `#pw` | так |
| Перевалідація | при зміні `#pw` повторно звіряти `#pw2`, якщо воно вже заповнене |

Повідомлення:
- порожнє → «Повторіть пароль»
- не збігається → «Паролі не збігаються»

#### 3.2.5. Нікнейм (`#nick`) — необов'язкове
Валідується **лише якщо заповнене**.

| Правило | Значення |
|---|---|
| Довжина | 3–20 символів |
| Дозволені символи | латинські літери, цифри, `_`, `.` |
| Не починається / не закінчується на `.` або `_` | так |
| Без подвійних `..` / `__` | так |
| Унікальність | 🔒 перевірка на сервері (async, debounce 400 мс) |

Regex: `^(?!.*[._]{2})[A-Za-z0-9](?:[A-Za-z0-9._]{1,18})[A-Za-z0-9]$`

Повідомлення:
- неправильний формат → «Нікнейм: 3–20 символів, латиниця, цифри, _ або .»
- зайнятий → «Цей нікнейм уже зайнятий»

#### 3.2.6. Дата народження (`#bday`) — необов'язкове
Валідується **лише якщо заповнене**. `input[type=date]` → значення `YYYY-MM-DD`.

| Правило | Значення |
|---|---|
| Валідна дата | так |
| Не в майбутньому | дата ≤ сьогодні |
| Мінімальний вік | ≥ 13 років 🔒 (узгодити; для ЄС часто 16) |
| Розумна нижня межа | не раніше 1900-01-01 |

Реалізація: задати `max` = сьогодні, `min` = сьогодні − 120 років. Вік рахувати точно
(з урахуванням місяця і дня).

Повідомлення:
- майбутнє → «Дата народження не може бути в майбутньому»
- вік < 13 → «Реєстрація доступна з 13 років»

#### 3.2.7. Згода з умовами (`#terms`) — обов'язкове
- Кнопка «Зареєструватися» неактивна, доки не поставлено галочку (вже є).
- Додатково на сабміті: якщо знято — показати помилку «Підтвердьте згоду з умовами».

### 3.3. Підсумок сабміту (реєстрація)
1. Нормалізувати всі поля.
2. Перевірити: ім'я, e-mail, пароль (політика), підтвердження, згода — **обов'язкові**.
3. Перевірити нікнейм і дату народження — **тільки якщо заповнені**.
4. Якщо є помилки → підсвітити, фокус на перше невалідне, **не відправляти**.
5. Якщо все ок → заблокувати кнопку, відправити на бекенд.
6. Відповідь:
   - успіх → показати `.alert.show` («Акаунт створено»), далі редірект/підтвердження пошти;
   - e-mail уже існує → польова помилка на e-mail «Користувач із таким e-mail уже існує»;
   - помилка сервера → банер form-level.

## 4. Сторінка «Вхід» (`login.html`)

### 4.1. Функціонал
- Поля: **E-mail**, **Пароль** (з показом/приховуванням).
- Чекбокс **«Запам'ятати мене»**.
- Посилання **«Забули пароль?»** → веде на `reset.html` (зараз `#` — виправити).
- Кнопка **«Увійти»**, соц-логін, посилання на реєстрацію.

### 4.2. Валідація
> На вході валідація **м'якша**: ми не перевіряємо політику паролю (перевіряємо вже **існуючий**
> пароль), лише що поля заповнені й e-mail схожий на e-mail.

#### 4.2.1. E-mail (`#email`)
- Не порожнє → «Введіть ваш e-mail».
- Базова перевірка формату (той самий regex, що в §3.2.2) → «Невірний формат e-mail».
- Позначити `<label>` як обов'язкове (`label--required`) — зараз у логіні зірочки немає.

#### 4.2.2. Пароль (`#pw`)
- Не порожнє → «Введіть пароль».
- **Без** перевірки довжини/складності.

### 4.3. Обробка відповіді (login-specific) 🔒
- Невірні дані → **загальний** банер «Невірний e-mail або пароль» (не уточнювати, що саме
  неправильне — щоб не давати підказку, чи існує такий e-mail).
- Забагато спроб → «Забагато спроб входу. Спробуйте за N хвилин» (rate limit на сервері).
- Акаунт не підтверджено → «Підтвердьте e-mail. Лист надіслано на …».
- «Запам'ятати мене»: впливає на час життя сесії/токена (довга vs коротка сесія).

## 5. Сторінка «Відновлення паролю» (`reset.html` — створити)

> **Наразі сторінки немає**, у логіні лише посилання-заглушка `«Забули пароль?»` → `#`.
> Створити нову сторінку в єдиному стилі (ті самі `tokens.css`/`typography.css`, hero-колонка,
> перемикач теми). Реалізувати як майстер із 3 кроків (на одній сторінці перемикати блоки,
> або кроки 1/3 на reset.html і крок 2 — на окремій сторінці за посиланням з листа).

### 5.1. Крок 1 — Запит на відновлення
- Поле: **E-mail** (валідація як у §3.2.2).
- Кнопка: «Надіслати інструкції».
- **Безпека (важливо)** 🔒: незалежно від того, існує акаунт чи ні, показувати **однакове**
  повідомлення: «Якщо акаунт із таким e-mail існує, ми надіслали лист з інструкціями».
  Так ми не розкриваємо, які e-mail зареєстровані (захист від енумерації).
- Rate limit на повторну відправку: кнопка з таймером (напр., «Надіслати ще раз через 60 с»).

### 5.2. Крок 2 — Перехід за посиланням із листа
- Лист містить одноразове посилання з токеном: `reset.html?token=…`.
- Токен 🔒: одноразовий, час життя 30–60 хв, перевіряється сервером.
- Якщо токен недійсний/прострочений → показати екран помилки + кнопку «Надіслати новий лист».

### 5.3. Крок 3 — Встановлення нового паролю
- Поля: **Новий пароль** + **Підтвердження** (валідація **повністю як у §3.2.3 і §3.2.4**:
  та сама політика, чек-лист вимог, індикатор надійності, показ/приховування).
- Додатково 🔒: новий пароль **не має дорівнювати старому** (перевірка на сервері).
- Кнопка: «Зберегти новий пароль».
- Успіх → повідомлення «Пароль змінено» + кнопка/редірект на «Вхід».
  Бажано 🔒 інвалідувати всі активні сесії після зміни паролю.

### 5.4. Потрібні ресурси
Іконки: вистачає наявних `#i-mail`, `#i-lock`, `#i-shield`, `#i-check`.
За бажанням додати `#i-key` для hero — не критично.

| Поле | Форма | Обов'язк. | Ключові правила | Приклад помилки |
|---|---|---|---|---|
| Ім'я | Реєстрація | так | 2–50, літери/`'`/`-`, є літера | «Введіть ваше ім'я» |
| E-mail | Реєстр./Вхід/Reset | так | формат RFC, ≤254, lowercase | «Невірний формат e-mail» |
| Пароль | Реєстр./Reset | так | 8–64, верх+низ+цифра+спецсимвол | «Пароль не відповідає вимогам» |
| Підтвердж. паролю | Реєстр./Reset | так | точний збіг | «Паролі не збігаються» |
| Нікнейм | Реєстрація | ні | 3–20, `[a-z0-9_.]`, унікальний | «Цей нікнейм уже зайнятий» |
| Дата народж. | Реєстрація | ні | не майбутнє, вік ≥13 | «Реєстрація доступна з 13 років» |
| Жанри | Реєстрація | ні | 0–6 значень | — |
| Згода | Реєстрація | так | має бути ✓ | «Підтвердьте згоду з умовами» |
| Пароль (вхід) | Вхід | так | лише непорожнє | «Введіть пароль» |

## 8. Нефункціональні вимоги

- **Безпека** 🔒: усі правки дублювати на сервері; паролі лише хешовані (bcrypt/argon2);
  HTTPS; CSRF-захист форм; rate limiting на вхід і на запит відновлення; не розкривати
  існування e-mail (§4.3, §5.1).
- **Продуктивність:** валідація синхронна, миттєва; async лише для перевірки унікальності нікнейму
  (debounce 400 мс, скасування попереднього запиту).
- **Сумісність:** сучасні браузери (Chrome/Firefox/Safari/Edge, 2 останні версії), мобільні.
- **Локалізація:** усі рядки повідомлень зібрати в один об'єкт `MESSAGES`, щоб легко перекладати.

## 9. Критерії приймання (acceptance) — тест-сценарії

**Реєстрація**
1. Порожня форма + сабміт → 4 обов'язкові поля підсвічені, фокус на «Ім'я», форма не відправлена.
2. `ім'я = "А"` → «щонайменше 2 символи»; `ім'я = "Іван123"` → помилка символів.
3. `email = "test@"` / `"a@b"` / `"a@@b.com"` / `"a..b@x.com"` → невалідні; `"User@Gmail.com"` → ок, нормалізується в `user@gmail.com`.
4. `пароль = "qwerty"` → чек-лист червоний, індикатор «Слабкий»; `"Qwerty12!"` → усі ✓, «Надійний».
5. Пароль і підтвердження різні → «Паролі не збігаються»; виправлення підтвердження прибирає помилку на льоту.
6. Нікнейм порожній → форма валідна; `"ab"` / `"_user"` / `"a..b"` → помилка.
7. Дата народження = завтра → помилка; вік 10 років → «з 13 років».
8. Без згоди кнопка disabled; зі згодою — активна.
9. Усе валідне → банер «Акаунт створено».

**Вхід**
10. Порожні поля → дві помилки.
11. Невірні дані → загальний банер «Невірний e-mail або пароль» (без уточнень).
12. «Забули пароль?» веде на `reset.html`.

**Відновлення**
13. Крок 1: будь-який валідний e-mail → нейтральне повідомлення (без розкриття існування).
14. Крок 3: новий пароль за політикою §3.2.3; розбіжність підтвердження → помилка; успіх → «Пароль змінено» + перехід на вхід.
15. Прострочений токен → екран помилки + «Надіслати новий лист».

**Спільне**
16. Невалідний `input` має `aria-invalid="true"` та `aria-describedby`.
17. Усі форми проходяться лише з клавіатури; видимий фокус скрізь.
18. Світла/темна теми коректні на всіх трьох сторінках.

## 10. Обсяг робіт (для оцінки)
1. Спільний модуль валідації (`validators` + `MESSAGES`).

3. Рефакторинг `login.js`: валідація §4, банер form-level помилок, лінк на reset.

5. Доступність (aria-*, фокус, клавіатура) на всіх формах.
6. Прогін тест-сценаріїв §9.
